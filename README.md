# Today

One page for what today holds: the next thing, what is due, and what is worth
knowing. It is a Leo **app package** — a descriptor plus a small process — so
it installs over a running hub with no rebuild of Leo and no checkout.

```bash
git clone https://github.com/TheBananaStand/leo-today /tmp/leo-today
leo packages install /tmp/leo-today/today.descriptor.json --enabled

# The page needs a credential to read the hub with. See "The token" below
# for why this step is not automatic yet.
leo packages token mint today --scope calendar:read,reminders:read,feed:read --label "Today's Graph reads"
leo packages set today today_graph_token=<the token it printed>
leo packages disable today && leo packages enable today   # respawn, so it picks the token up
```

Then open **Today** in the sidebar, or go to `/p/today/today`.

## The token, and why that step exists

A package declares what it needs to read as `entitlements.graph_scopes`, and
this one declares `calendar:read`, `reminders:read`, `feed:read`. The install
consent shows them. **They are never minted for an app package:**
`graph_scopes_for()` in `crates/leo-package/src/manager.rs` builds its scope
list from `entitlements.inference` alone, so an app that declares Graph scopes
and nothing else is spawned with no `LEO_PACKAGE_TOKEN` at all. The call site's
own comment says an entitled app gets the credential to reach back with; that
is true only for inference.

So the token comes the other supported way — a settings key this package
declares in `settings_read`, which the hub hands to the process as an
environment variable at spawn. When the mint path is fixed, the three lines
above collapse into the first one and nothing else here changes.

**Reading for a person is separate from that.** Reminders and the feed answer
for ONE person and refuse a bare package credential outright. The hub stamps a
single-use grant (`x-leo-acting-grant`) on its call to `/leo/ui/data`; this
spends it at `/graph/v1/acting/exchange` and carries the result on those two
reads, so the page is each person's own. The calendar is a household domain
and keeps the package credential.

## What it is made of

| File | What it is |
|---|---|
| `today.html` | the whole screen, in Leo's HTML subset (`leo examples show docs/html-subset.md`) |
| `leo-today` | the process behind it: fetches a few hub domains over the Graph, answers `GET /leo/ui/data`, and serves the three presses on `POST /leo/ui/action` |
| `build.py` | puts the markup into `today.descriptor.json` — the markup stays a file you can open in a browser |
| `samples/*.json` | the four states the screen was designed against: ready, empty, nothing-answered, and awkward data. **Generated by `selftest.py`, which drives the real `payload()`** — they were hand-written once, went stale when the payload was rewritten, and two of them then drew the same picture for months without anybody noticing |

## The two ideas worth stealing

**The page is data, the payload decides what is on it.** Every block is gated
on having something in it (`if="events"`), and an empty array is false in this
language — so a quiet day is a short page and a busy one is a long page, with
no code choosing. Ordering, capping and wording all live in the payload, which
is why the markup never changed while the process was rewritten.

**Every source fails on its own.** The three sources are fetched in parallel
with a 2.5s budget each. One that errors, times out, or that this package's
token may not reach leaves its key missing: its block is simply absent, the
others are unaffected, and a line at the foot says which one did not answer.
Only when *nothing* answers does the page become an error state — with a way
out. A page that is down whenever any one package is down is not a page you
would keep open.

## The three presses

`GET /leo/ui/data` is what fills the page. `POST /leo/ui/action` is what the
presses reach — the hub's own channel for an app package, forwarded from
`/api/packages/today/ui/action` with the person's id in `x-leo-user-id`.

| `name` | What it does |
|---|---|
| `ask` | Files the question, hands the model call to a thread, returns at once. The answer arrives by `nudge()` on the `today` topic, which `refreshOn` already listens to |
| `clear` | Forgets the last answer |
| `rewrite` | Drops the cached briefing, so the next draw rebuilds it |

**A model call never happens on the request path.** A press is something a
finger is waiting on and a model is seconds; the briefing already solved this
by writing on a thread and nudging the open page, and Ask uses the same
machinery rather than a second one. The page therefore has three Ask states —
in flight, answered, and could-not-answer — and renders all three.

**Declare these as `packageAction`, not as a hand-written HTTP call.** That
is the action kind that reaches a package's `ui_action`, and the hub forwards
it as `{"name": "ask", "args": {"text": "..."}}` with the person in
`x-leo-user-id`:

```json
"ask": {"kind": "packageAction", "name": "ask",
        "args": {"text": "{args.text}"}, "refresh": "reload"}
```

Two HTTP spellings were tried first and **both returned 200 while doing
nothing**, which is why they are written down in `build.py` rather than
quietly replaced:

* a templated **body** is passed through VERBATIM, so the process was handed
  the literal string `{args.text}` as the question -- and the model answered,
  correctly, that it could not see a question;
* a templated **query** is stripped when the hub proxies, and the hub fills
  its own `{name, args}` body, which for a generic HTTP action is
  `{"args": null, "name": ""}`.

`docs/package-ui.md` names the right one in a single line -- `ui_action` is
"server-computed mutations for `packageAction`" -- and `leo-apple`'s
`photos_app.rs` has it in an actions map. Neither was reachable by reasoning
about the wire; it took logging what actually arrived.

## Ask

At the foot of the page is a thread. `<conversation>` **draws nothing** — it
owns the socket and the transcript and hands the markup a scope, so the turns
are Today's own type and spacing rather than a chat window dropped onto the
page. The composer is markup too.

The socket is this process. The app proxy bridges a WebSocket upgrade at
`/p/today/chat` straight through to it with no per-app code, stamping the
asker's identity **and a single-use acting grant** on the handshake exactly as
it does on a UI-data request — so the thread is told whose day it is about and
can answer from the same data the page is showing.

It sits at the foot deliberately: the blocks above keep their places whatever
is said here. A page that re-arranged itself while you talked to it would cost
you the one thing a glance page is for.

**The model comes from the hub.** This package holds no key and names no
model: it sends `work: conversation` and the household's own routing, ceiling
and costs page apply. One wrinkle, worth knowing if the thread answers with an
error on a fresh hub — the built-in model catalog prices exactly **one** model,
so the household default (`claude-opus-5`) is refused for a package call:

> model `claude-opus-5` is in this hub's catalog but declares no rate, so a
> call to it would be billed at $0 and would never count against the household
> ceiling

That refusal is right — billing a package at zero is worse than refusing it —
but it means no package can ask a model at all until someone edits
`model_catalog`. So on exactly that refusal this asks again as
`periodic_check`, the work class that routes to the `fast` role, which is the
one priced entry. Still never naming a model. Pricing your real default is the
owner's to do, and then the first call succeeds.

## What it does not do yet

- **Three sources.** Calendar, reminders, feed. Adding a fourth is a function
  and a scope, and the markup only changes if the block is a new *shape*.
- **The ordering is fixed**, not scored. Blocks appear in a set order; only
  their presence varies.
- **The thread does not stream.** It answers in one `result` frame. The
  element handles a streamed turn (`live.text` is already in the markup);
  this process just doesn't send deltas yet.
- **The thread cannot act.** It answers about the day; it cannot tick
  something off for you.

## Scopes it asks for

`calendar:read`, `reminders:read`, `feed:read` — read-only. Ticking a reminder
goes through the route Reminders already serves to a person, so the page holds
no privilege of its own.
